# CRM Bitrix24 (Funil, Vendedores, Origens) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Sincronizar leads e negócios do funil Brinde do Bem do Bitrix24 para o Supabase 3x/dia e mostrar as telas Funil, Vendedores e Origens, com o perfil Vendedor vendo só os próprios registros.

**Architecture:** O mesmo padrão do Mercado Livre. O conector TypeScript (`packages/connectors/src/bitrix24`) lê a REST via webhook. O job (`jobs/src/sync-bitrix24.ts`) grava no schema `crm`. As funções SQL `analytics.crm_*` calculam tudo e as páginas Next.js só mostram. O RLS do banco aplica a regra do perfil Vendedor.

**Tech Stack:** Node 22/24 + TypeScript (tsx, `node --test`), `postgres` (jobs), Supabase Postgres (RLS, funções SQL), PGlite (testes SQL), Next.js 15 + Tailwind (apps/web).

**Spec:** `docs/superpowers/specs/2026-11-13-crm-bitrix24-design.md`

## Global Constraints

- A URL do webhook (`BITRIX_WEBHOOK_URL`) nunca aparece em log, erro, arquivo ou commit. Os rótulos de erro são `bitrix:<método>` (o `BitrixClient` já existe em `packages/connectors/src/bitrix24/client.ts`).
- O job **só lê** do Bitrix: só métodos `*.list`, `*.fields`, `*.get` e `batch`. Nunca `*.add`, `*.update` nem `*.delete`.
- Privacidade: os leads são buscados sem título, e-mail e telefone. Não usar `select: ['*']` nem `UF_*` além de `UF_CRM_1740402485`. Não gravar `raw` completo.
- Funil: só `CATEGORY_ID = 10` (Brinde do Bem). Leads: só os de `SOURCE_ID` presente em `crm.origens_brinde` com `ativo`.
- Origens iniciais (seed): `19`, `38`, `10|WHATSAPP`, `52|BITRIX_WHATCRM_NET_70680444`, `39`, `23`, `53`, `42`, `24`, `14|FACEBOOK`, `54`.
- Motivo de perda = a etapa de perda. `C10:LOSE` é exibido como "Cancelado (sem motivo)".
- Campo Área de Negócio: `UF_CRM_1740402485`, enumeração cujo ID do item é convertido para o rótulo (Brinde do Bem | Brindes Vocação | Pedido Online).
- Datas: o Bitrix devolve horário com fuso (`+03:00`). Grava como `timestamptz`. O dia de referência é `(ts at time zone 'America/Sao_Paulo')::date`.
- `core.sync_runs.source = 'bitrix24'` (é o valor que o check da 0001 aceita). O canal RLS é `'crm'`.
- Novas permissões: `crm_funil`, `crm_vendedores` e `crm_origens`. Valores iniciais: admin, gestor, comercial e vendedor = true; visualizador = false.
- Migrations reexecutáveis (`create … if not exists`, `create or replace`, `on conflict do nothing`), com o mesmo padrão `(select core.fn())` da 0011 nas políticas.
- Commits terminam com `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`. Git em `C:\Program Files\Git\cmd\git.exe`.
- Textos de tela em português simples (o dono é leigo).

### Task 2: Funções de análise `analytics.crm_*`

**Files:**
- Create: `supabase/migrations/0013_crm_funcoes.sql`

**Interfaces:**
- Consumes: as tabelas da Task 1.
- Produces (todas `stable`, `security invoker` exceto `crm_vendedores`, parâmetros `p_de date, p_ate date, p_area text default null, p_vendedor bigint default null, p_origem text default null`). Os filtros se aplicam assim: `p_area` → `deals.area`; `p_vendedor` → `assigned_by_id`; `p_origem` → `leads.source_id` nas contagens de lead e `deals.source_id` nas de negócio. Leads e negócios com `deleted_at` ficam sempre fora. Só leads cujo `source_id` está em `origens_brinde` ativas. Só negócios com `category_id = 10`.
  - `analytics.crm_resumo(...) returns table(leads_novos int, leads_com_negocio int, negocios_coorte int, ganhos_coorte int, ganhos int, perdidos int, valor_ganho numeric, ciclo_medio_dias numeric)`. Os cartões mostram `% lead→negócio = leads_com_negocio/leads_novos` e `% negócio→ganho = ganhos_coorte/negocios_coorte`
  - `analytics.crm_funil(...) returns table(ordem int, etapa text, quantidade int)`: Leads; Negócios (da coorte); cada etapa `andamento` do funil 10, com os negócios da coorte que tiveram entrada nela no `stage_history`; Ganhos (da coorte)
  - `analytics.crm_etapas(...) returns table(status_id text, nome text, ordem int, em_aberto int, valor_aberto numeric, tempo_medio_dias numeric, gargalo boolean)`. `em_aberto` e `valor_aberto` são a foto de **agora**, sem período. `tempo_medio_dias` vem das entradas na etapa dentro do período: saída = próxima entrada do mesmo negócio, ou `now()` se o negócio continua nela. `gargalo` marca a etapa de maior `tempo_medio_dias`
  - `analytics.crm_motivos_perda(...) returns table(status_id text, motivo text, perdidos int, pct numeric)`. `motivo` = nome da etapa, e `C10:LOSE` aparece como `'Cancelado (sem motivo)'`. Considera os perdidos com `closedate` no período
  - `analytics.crm_vendedores(...) returns table(bitrix_id bigint, vendedor text, leads int, primeiro_contato_horas numeric, sem_contato int, negocios int, ganhos int, perdidos int, conversao numeric, valor_ganho numeric, ticket_medio numeric)`, **security definer**. Começa exigindo `core.has_perm('crm_vendedores')`. Se `core.my_role() = 'vendedor'`, devolve só a linha de `core.my_bitrix_id()` mais a linha `(null, 'Média da equipe', …médias de todos os vendedores com atividade no período)`. Responsável nulo vira a linha `(null, 'Sem responsável')`. `conversao = ganhos/(ganhos+perdidos)`
  - `analytics.crm_origens(...) returns table(source_id text, origem text, leads int, pct_negocio numeric, pct_ganho numeric, valor_ganho numeric, ticket_medio numeric)`. Os leads são da coorte, pela origem do lead. Valor ganho e ticket vêm dos negócios ganhos no período, pela origem do negócio. A origem nula aparece como "Sem origem"
  - `analytics.crm_opcoes() returns table(tipo text, valor text, rotulo text)`: `area`, `vendedor` (com o RLS valendo, o vendedor só vê a si mesmo) e `origem`
  - `grant execute … to authenticated` em todas

Regras (spec §4): leads novos pela data de criação; coorte = leads criados no período, com o desfecho até hoje; ganhos, perdidos e valor pela `closedate` no período e pela semântica da etapa; ciclo = `closedate − date_create` dos ganhos no período; 1º contato = `first_activity.primeira_em − leads.date_create`, sem os leads que não têm atividade (contados em `sem_contato`). Toda data é comparada como `(ts at time zone 'America/Sao_Paulo')::date between p_de and p_ate`.

  1. Abre o `core.sync_runs` com `source 'bitrix24'`. O incremental parte da última execução com sucesso − 1 h; sem execução anterior, é a carga completa
  2. Configuração: `crm.category.list` → `crm.pipelines`; `crm.status.list` → `crm.stages` (os `STATUS` como `lead` e os `DEAL_STAGE_10` como `deal`, com o `C10:` mantido) e `crm.sources`; `crm.deal.fields` → o mapa das áreas; `user.get` (paginado) → `crm.users` (nome = `NAME + ' ' + LAST_NAME`, `EMAIL`, `ACTIVE`)

Os negócios com `CATEGORY_ID = 10` recebem upsert; os que chegam com outro funil e existem em `crm.deals` são **apagados** de `crm.deals` (e do `stage_history`)
  5. Histórico: `listarPorId('crm.stagehistory.list', { filter: { CATEGORY_ID: 10, '>ID': maior id gravado }, select: ['ID','OWNER_ID','STAGE_ID','CREATED_TIME'] }, { itens: r => r.items })`, com o parâmetro extra `entityTypeId: 2` → `crm.stage_history`
